## 1.2 Аналіз існуючих аналогів

Для аналізу обрано три системи обміну повідомленнями, що розв’язують задачу захищеної комунікації: Signal, WhatsApp і Telegram. Системи розглянуто як інженерні об’єкти за чотирма аспектами: архітектурний патерн, протоколи передачі даних, стек даних і механізми консистентності, відомі технічні обмеження (Technical Bottlenecks). Відомості отримано з відкритого вихідного коду, офіційних специфікацій протоколів, інженерних публікацій розробників і рецензованих досліджень.

### 1.2.1 Signal

Signal побудовано як централізовану клієнт-серверну систему. Серверне ядро Signal-Server є модульним монолітом на Java 21 (Dropwizard: Jersey + Jetty), вузли якого не зберігають стану й масштабуються горизонтально за балансувальником навантаження. Функції, критичні для приватності, винесено в окремі сервіси, що виконуються в апаратних анклавах Intel SGX: пошук контактів (CDSI) і відновлення ключів (SVR2/SVR3, з розподілом довіри між анклавами різних хмарних провайдерів). Групові дзвінки обслуговує окремий SFU (Signal-Calling-Service). Клієнтська криптографія реалізована в бібліотеці libsignal (Rust) з прив’язками для Java, Swift і TypeScript.

Взаємодія клієнта із сервером здійснюється через REST/HTTPS, постійне WebSocket-з’єднання з кадрами Protocol Buffers і gRPC для частини API; офлайн-клієнти отримують push-сповіщення через FCM/APNs. Сесія встановлюється протоколом PQXDH (X25519 + Kyber-1024), повідомлення захищаються Double Ratchet, а з жовтня 2025 року – Triple Ratchet із постквантовим механізмом SPQR (Sparse Post-Quantum Ratchet, ML-KEM-768). Для груп застосовано Sender Keys та анонімні облікові дані zkgroup; механізм Sealed Sender приховує від сервера ідентичність відправника.

Стек даних включає Amazon DynamoDB (облікові записи, ключі, черги повідомлень), Redis Cluster у чотирьох ролях (кеш, pub/sub, rate limiting, планувальник push-сповіщень), FoundationDB як транзакційне сховище та S3 для вкладень. Доставка повідомлень двоярусна: запис виконується в Redis (`MessagesCache`), після чого фоновий процес `MessagePersister` асинхронно переносить дані в DynamoDB; вибірка об’єднує обидва джерела, а повідомлення видаляється після підтвердження доставки клієнтом. Історія листування на сервері не зберігається.

До технічних обмежень належать: client-side fan-out, за якого кожне повідомлення шифрується окремо для кожного пристрою; вартість ротації Sender Key порядку O(N) парних повідомлень у групі з N учасників; відсутність post-compromise security у групі до наступної ротації; ліміт групи в 1000 учасників; залежність від довіри до Intel SGX, для якого відомі side-channel атаки; прив’язка реєстрації до номера телефону; залежність від керованих сервісів AWS (vendor lock-in).

### 1.2.2 WhatsApp

Серверна частина WhatsApp побудована на Erlang/OTP: кожне клієнтське з’єднання обслуговує легковаговий процес віртуальної машини BEAM. За даними доповіді WhatsApp на Code BEAM 2024, кластер налічує понад 40 000 вузлів, об’єднаних Erlang Distribution, service discovery реалізовано через модуль `pg`, кількість одночасних з’єднань перевищує 1 млрд. З 2017 року інфраструктуру перенесено з IBM SoftLayer у власні дата-центри Meta, а FreeBSD замінено на Linux. Серверний і клієнтський код закритий; компоненти клієнтів, що обробляють недовірені дані, переписуються на Rust (медіабібліотека wamedia, 2026 рік).

Транспорт захищено протоколом Noise Pipes (Curve25519, AES-GCM, SHA-256); прикладним протоколом є власний бінарний FunXMPP¹. Наскрізне шифрування базується на Signal Protocol (X3DH, Double Ratchet), групи використовують Sender Keys із server-side fan-out. Підтримку кількох пристроїв (multi-device, 2021) реалізовано через окремий identity key для кожного пристрою та client-side fan-out; підтримується до чотирьох додаткових пристроїв. Автентичність відкритих ключів контролюється механізмом Key Transparency на основі Auditable Key Directory (AKD, 2023).

Стек даних, за відкритими доповідями, базується на Mnesia – розподіленій СУБД Erlang із реплікацією між вузлами, у якій зберігаються таблиці маршрутизації, офлайн-черги та дані користувачів¹. Застосовано модель store-and-forward: повідомлення зберігається на сервері лише до доставки, яку підтверджують квитанції. Резервні копії розміщуються в iCloud або Google Drive; наскрізне шифрування резервних копій опційне, ключ зберігається в HSM-сховищі (Backup Key Vault).

До технічних обмежень належать: закритий код, що унеможливлює незалежний аудит реалізації; доступність метаданих оператору (соціальний граф, час, IP-адреси, книга контактів); відсутність наскрізного шифрування резервних копій за замовчуванням; зростання трафіку пропорційно кількості пристроїв через client-side fan-out; відсутність post-compromise security у групах до ротації Sender Keys; ліміт групи в 1024 учасники; обмеження масштабування повнозв’язної топології Erlang Distribution, для подолання якого глобальний реєстр `global` замінено на `pg`.

¹ За доповідями 2012–2014 рр.; поточна конфігурація не розкривається, інформація може бути застарілою.

### 1.2.3 Telegram

Telegram є централізованою розподіленою системою з п’ятьма дата-центрами (Маямі, Амстердам, Сінгапур); кожен обліковий запис закріплено за «домашнім» дата-центром. Серверний код закритий; за неофіційними даними, сервер реалізовано мовою C++. Клієнти відкриті: Telegram Desktop – C++/Qt, бібліотека TDLib – C++, Android-клієнт – Java з нативними компонентами C++ (JNI), iOS-клієнт – Swift/Objective-C.

Обмін даними здійснюється власним протоколом MTProto 2.0, що складається з трьох рівнів: API із TL-серіалізацією; криптографічний рівень (AES-256-IGE, `msg_key` на основі SHA-256, `auth_key` через DH-2048); транспортний рівень (TCP, WebSocket, HTTP(S) з обгортками Abridged, Intermediate, Padded Intermediate, Full). У cloud chats шифрування застосовується лише на ділянці клієнт–сервер. Наскрізне шифрування доступне тільки в secret chats: лише 1:1, із прив’язкою до пристрою, вимкнене за замовчуванням, з оновленням ключа кожні 100 повідомлень або раз на тиждень. Групи й канали наскрізного шифрування не мають.

Сховище даних закрите й розподілене; історія cloud chats зберігається на сервері, зашифрована ключами сервера, які, за заявою розробника, розподілено між юрисдикціями. Консистентність забезпечується послідовностями оновлень `pts`, `qts` і `seq`: розрив виявляється за умовою `local_pts + pts_count < pts` і заповнюється методами `updates.getDifference` та `updates.getChannelDifference`, що виключає пропуск і повторне застосування оновлень. Cloud chats синхронізуються між необмеженою кількістю пристроїв; secret chats доступні лише на одному пристрої.

До технічних обмежень належать: відсутність наскрізного шифрування за замовчуванням і в групах, унаслідок чого сервер має доступ до вмісту cloud chats; власна криптографія, для якої Albrecht et al. (IEEE S&P 2022) описали чотири атаки на MTProto 2.0, зокрема відновлення відкритого тексту через timing side-channel у трьох офіційних клієнтах; відсутність синхронізації secret chats між пристроями; зниження доступності облікового запису при відмові домашнього дата-центру; неможливість незалежного аудиту серверної частини.

Проведений аналіз виявив два архітектурні підходи до захищеного обміну повідомленнями. У Telegram пріоритет надано синхронізації між пристроями та масштабу аудиторії ціною відмови від наскрізного шифрування за замовчуванням: сервер зберігає історію cloud chats у доступному для себе вигляді, наскрізне шифрування груп відсутнє, а для протоколу MTProto 2.0 опубліковано чотири атаки. Signal і WhatsApp забезпечують наскрізне шифрування за замовчуванням на основі Signal Protocol, проте підтримку кількох пристроїв реалізовано через client-side fan-out, а групові Sender Keys відновлюють безпеку після компрометації лише в момент ротації. Для WhatsApp додатково характерні закритий код і доступ оператора до метаданих, для Signal – залежність від довіри до Intel SGX і від керованих сервісів AWS.

У межах кваліфікаційної роботи обрано схему sender-key ratchet з явною моделлю епох ключів. Епоха є серверним записом (`chat_id`, `epoch`, `member_set_hash`, `reason`), що не містить ключового матеріалу. Ротація виконується атомарно разом зі зміною складу групи, відкликанням пристрою та за розкладом. Перед розсиланням ключів клієнт звіряє склад групи з commitment епохи, що унеможливлює непомітне додавання учасника сервером. Вартість розсилання ключів становить S×(N−1) грантів на епоху, де S – кількість активних відправників, тоді як попарні сесії Double Ratchet у групі потребують O(N²); відповідно, розмір зашифрованої групи обмежено 256 учасниками. Для каналів застосовано підпис Ed25519: для відкритої трансляції конфіденційність недосяжна, тоді як автентичність зберігається з вартістю O(1) на публікацію. Серверний стек побудовано за принципом Polyglot Persistence: PostgreSQL – для транзакційних сутностей епох, пристроїв і грантів; MongoDB – для незмінних зашифрованих конвертів; Redis – для присутності, pub/sub і брокера Celery; MinIO – для зашифрованих вкладень. Розгортання через Docker Compose не прив’язане до керованих сервісів конкретного хмарного провайдера.

Обраний підхід передбачає явний архітектурний компроміс. Forward secrecy забезпечується односпрямованим KDF-ланцюжком у межах епохи, а post-compromise security – лише на межі епохи, а не для кожного повідомлення, як у попарному Double Ratchet. Метадані залишаються доступними серверу. Відсутність серверної черги офлайн-доставки з підтвердженням і TLS-термінації на Nginx визначено як обмеження поточної реалізації. Звідси випливають вимоги до Розділу 2: проєктування черги доставки з підтвердженнями (Redis Streams, consumer groups), схеми розгортання з TLS і формалізація моделі епох у нотаціях C4 та UML.
