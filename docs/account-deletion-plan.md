# План: видалення облікового запису та обмеження схеми даних

Другий пакет змін після `docs/hardening-plan.md`. Одна гілка, один Pull Request. Охоплює
TB-28 (видалення облікового запису) та TB-21, 22, 23, 25 (обмеження й індекси PostgreSQL).

## 1. Рішення щодо повідомлень

Повідомлення **не видаляються**. Видалення облікового запису стирає персональні дані та
доступ до акаунта, але не вміст чатів, які належать також іншим учасникам.

Фізичне видалення рядка `users` неможливе без втрати історії: зовнішні ключі з
`ON DELETE CASCADE` знищили б ключі ідентичності, розподіли ключів відправника та гранти
(`user_identity_keys`, `sender_key_distributions`, `sender_key_grants`). Після цього
інші учасники не змогли б ні розшифрувати, ні перевірити підпис давніх повідомлень.

Тому застосовується **знеособлення з надгробком** (tombstone):

| Дані | Що відбувається |
|---|---|
| Рядок `users` | Лишається. `username`, `full_name`, `email`, `phone`, `avatar_url`, `bio` замінюються нейтральними значеннями або `NULL`; пароль знищується; `is_active = false`; `deleted_at = now()` |
| Приватні пакети ключів (`encrypted_private_bundle`, застарілі RSA-поля) | Знищуються. Нікому більше не потрібні |
| Пристрої | Відкликаються (`revoked`), сесії завершуються (`force_logout`) |
| Публічні ключі, підписи, розподіли ключів відправника, гранти | **Лишаються**, щоб історію можна було відкрити і перевірити |
| Повідомлення в MongoDB | **Лишаються без змін**; `sender_id` указує на надгробок |
| Членство в чатах | Видаляється; у кожному зашифрованому чаті відкривається нова епоха (ротація в тій самій транзакції) |
| Контакти, папки, пакети стікерів, підписки, запрошення | Видаляються |
| Аватар в об'єктному сховищі | Видаляється |
| Журнал `security_audit` | Записується подія `account_deleted` без персональних даних |

Якщо користувач є власником групи, володіння автоматично переходить до найстаршого
адміністратора, а за його відсутності до найстаршого учасника (за `joined_at`). Якщо в
групі нікого не лишається, чат видаляється разом із повідомленнями, бо в ньому немає
інших власників даних. Особисті (1:1) чати лишаються лише для читання: історія видима,
автор показаний як «Видалений користувач», надсилати нові повідомлення неможливо
(відповідь 409 `PEER_DELETED`).

Клієнт показує автора як «Видалений користувач»; розшифрування і перевірка підпису
працюють як раніше. Про вибір слід зробити запис ADR-002 у репозиторії документації.

## 2. Що реалізується

### 2.1. TB-28. `DELETE /profile`

- Тіло: `{ "password": "..." }`, повторне введення пароля обов'язкове; `extra="forbid"`.
- Обмеження частоти як у зміни пароля.
- Усе в PostgreSQL виконується в одній транзакції; очищення об'єктного сховища та Mongo
  (реакції, закріплення) після неї, з журналюванням збоїв.
- Клієнт: кнопка в налаштуваннях профілю з підтвердженням і введенням пароля; після успіху
  вихід із системи; відображення «Видалений користувач» у списках, повідомленнях,
  інформації про чат.
- Прийняття: після видалення вхід неможливий; повідомлення залишаються у чатах і
  розшифровуються іншими учасниками; перевірка підпису проходить; чужі групи отримали нову
  епоху; рядок `users` не містить персональних даних; є подія аудиту.

### 2.2. TB-21. Розмірність і CHECK-обмеження криптографічних полів

- Публічні ключі (`identity_public_key`, `signing_public_key`, `signed_prekey_public`,
  `ephemeral_public_key`, `sender_key_distributions.signing_public_key`): `char(43)` та
  `CHECK (length = 43)`.
- Підписи: `char(86)` та `CHECK`.
- `chat_key_epochs.member_set_hash`: `char(64)` та `CHECK (member_set_hash ~ '^[0-9a-f]{64}$')`.
- `chat_participants.last_read_message_id`, `history_start_message_id`: `char(24)`.
- Перед міграцією перевірити, що наявні дані проходять обмеження; міграція переривається з
  переліком порушників, а не мовчки.

### 2.3. TB-22. Інваріанти епох

- Частковий унікальний індекс `uq_open_epoch_per_chat` на `chat_key_epochs (chat_id)
  WHERE closed_at IS NULL`.
- Складений зовнішній ключ `sender_key_distributions (epoch_id, chat_id)` на
  `chat_key_epochs (id, chat_id)`; для нього потрібен `UNIQUE (id, chat_id)`.

### 2.4. TB-23. Індекси

`ix_grant_recipient_device`, `ix_grant_recipient_identity_key`, `ix_chats_updated_at`.

### 2.5. TB-25. Обмеження допоміжних таблиць

- `chat_invite_links`: `CHECK (max_uses IS NULL OR use_count <= max_uses)`.
- `contacts`: `CHECK (owner_id <> contact_id)`.
- `stickers`: `UNIQUE (pack_id, position)`.

## 3. Вимоги до міграцій

- Один ланцюжок Alembic, кожна міграція має працюючий `downgrade()`; для кожного нового
  перелічуваного типу явний `DROP TYPE IF EXISTS`.
- Перевірити повний цикл `upgrade head`, `downgrade -1`, `upgrade head` на базі з тестовими
  даними.
- Нові моделі імпортуються в `alembic/env.py`.

## 4. Порядок виконання

1. Серверна частина TB-21…23, 25 (міграції, моделі, схеми, тести).
2. Серверна частина TB-28 (надгробок, служба видалення, маршрут, ротація епох, аудит, тести).
3. Клієнт: кнопка видалення та відображення «Видалений користувач».
4. Огляд коду та безпековий огляд, виправлення.
5. Документація: `tech-debt.md` (закрити пункт «Немає видалення облікового запису»).

Серверні кроки 1 і 2 виконуються послідовно, бо обидва додають міграції.

## 5. Наступний пакет (окрема гілка та PR)

розсилання).

## 6. Обмеження

- Коміти без співавторів та підписів Claude; `CLAUDE.md` і `.claude/` не комітяться.
- Після змін криптографічного шару виконується `npm run interop`.
- Інтеграційні тести виконуються з увімкненим rate limiting.
- Гілка створена від `main`; ту саму область (повідомлення, автентифікація) змінює PR #6,
  тому при злитті можливі конфлікти в тестах.
