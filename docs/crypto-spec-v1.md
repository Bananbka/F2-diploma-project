# Mess&Gags Wire Format v1

Normative specification for the end-to-end encryption layer. The reference implementation lives in
`api/app/domains/crypto/reference/` and the known-answer tests in `api/tests/crypto/` pin every
behaviour described here. **Where this document and the reference implementation disagree, the
tests decide.**

Keywords MUST / MUST NOT / SHOULD are used in the RFC 2119 sense.

> **Status.** All sections are frozen and implemented.

---

## 1. Conventions

| Thing | Encoding |
|---|---|
| Binary in JSON | base64url, **unpadded** (`b64u`) |
| Integers in AAD / signatures | 4-byte big-endian (`u32be`) |
| UUIDs in AAD / signatures | 16 raw bytes (`uuid.bytes`), **never** the hyphenated string |
| AEAD | AES-256-GCM, 12-byte nonce, 16-byte tag |
| KDF (chain) | HKDF-SHA256, empty salt |
| KDF (password) | Argon2id |
| Signatures | Ed25519 |
| Key agreement | X25519 |

### Domain separators

Every signed or AEAD-bound blob is prefixed with one, so a value produced for one purpose can never
be replayed as a value for another.

```
NS-v1-idbind       identity key binding
NS-v1-msg          message AAD
NS-v1-msgkey       HKDF info: chain key -> message key
NS-v1-chain        HKDF info: chain key -> next chain key
NS-v1-grant        sender key grant AAD
NS-v1-skdm         sender key distribution signature
NS-v1-skipped      AAD prefix: retained skipped key at rest (3.1)
NS-v1-skipped-key  HKDF info: KEK -> at-rest wrap key (3.1)
NS-v1-fingerprint  safety number
```

## 2. Identity

Each **device** holds two keypairs. They MUST be distinct keys: reusing one key across a signature
scheme and a DH scheme is a known cross-protocol hazard.

| Key | Algorithm | Purpose |
|---|---|---|
| Signing key | Ed25519 | Signs messages and distributions. Root of authenticity. |
| Identity key | X25519 | Receives wrapped sender keys via ECDH. |
| Signed prekey | X25519 | Optional, rotated ~weekly. Forward secrecy for grants. |

### 2.1 Binding

The X25519 key MUST be signed by the Ed25519 key:

```
binding = "NS-v1-idbind" || user_id(16) || device_id(16) || identity_public(32)
signature = Ed25519(signing_private, binding)
```

Binding `user_id` and `device_id` prevents a valid (key, signature) pair being transplanted onto
another identity. The server MUST verify this on publish and reject on failure.

`device_id` is generated by the **client** and persisted locally — the client signs over it, so a
server-assigned id would require a second round trip.

### 2.1.1 Signed prekey binding

The signed prekey MUST carry its own signature, under a **separate** domain separator:

```
binding = "NS-v1-prekeybind" || user_id(16) || device_id(16) || signed_prekey_public(32)
signature = Ed25519(signing_private, binding)
```

The separator differs from `NS-v1-idbind` deliberately. Both sign a 32-byte X25519 public key for the
same `(user_id, device_id)`, so a shared separator would make the two signatures interchangeable — a
prekey signature could be replayed as an identity-key binding, and vice versa.

The server MUST verify this on rotation, against the signing key **already recorded** for that device
rather than one supplied in the same request; a self-certifying rotation would prove nothing. Rotation
MUST NOT change the identity key or supersede the key version. It MUST NOT invalidate a grant already
ingested by the recipient device. A grant published against the *previous* signed prekey but not yet
ingested at the moment of rotation remains openable for exactly one further rotation cycle — see
§2.1.2's `prev_prekey_private` grace window — but not beyond that: a grant that survives two rotations
still un-ingested is not guaranteed openable.

This matters because §7 prefers the signed prekey over the identity key as the ECDH recipient. An
unverified prekey would let anyone able to reach the rotation endpoint substitute a key they hold and
receive every subsequent sender key — precisely the substitution the signature exists to prevent.

The signature MUST be verified wherever a prekey enters the system, which includes the **publish**
path and not only rotation. Verifying on rotation alone left the identical substitution reachable
through registration.

### 2.1.2 Rotation

`PUT /crypto/identity/prekey` rotates the prekey. It was disabled for a full incident cycle — see
below — and is re-enabled now that the private bundle (§2.2) has somewhere to keep the new prekey's
private half. Rotation MUST NOT change the identity key or supersede the key version; it changes
exactly the prekey columns and the stored bundle, atomically.

Rotation MUST NOT invalidate a grant the recipient device has already ingested. It also gives a
one-cycle grace window to a grant that was published against the *outgoing* prekey but not yet
ingested when rotation happens: the client carries that prekey's private half forward as
`prev_prekey_private` (§2.2) for exactly one further rotation. A grant still un-ingested after a
*second* rotation is not guaranteed openable — `prev_prekey_private` holds only the immediately
preceding generation, not an unbounded history.

The client:

1. Generates a fresh X25519 keypair.
2. Signs the public half under §2.1.1 with the device's *existing* signing key.
3. Re-seals its **entire** private bundle — the same JSON shape as §2.2, now with the new
   `prekey_private`, and with the *outgoing* `prekey_private` carried forward as
   `prev_prekey_private` (dropping whatever `prev_prekey_private` held before, if any) — under the
   KEK it already holds from unlock. No password prompt is needed: rotation happens with the
   session key already in memory.
4. Submits all three together:

```json
PUT /crypto/identity/prekey
{
  "device_id": "<uuid>",
  "signed_prekey_public": "<b64u, 32 bytes>",
  "signed_prekey_signature": "<b64u, 64 bytes>",
  "encrypted_private_bundle": "<b64u>",
  "kdf_params": {"kdf":"argon2id","m":...,"t":...,"p":...,"salt":"<b64u>","nonce":"<b64u>"}
}
```

The server verifies `signed_prekey_signature` against the signing key **already on record** for
the device (never one supplied in the same request — see §2.1.1), then writes the new
`signed_prekey_public`/`signed_prekey_signature`/`signed_prekey_created_at` and the new
`encrypted_private_bundle`/`kdf_params` in one transaction. Splitting that into two requests — or
two separate writes on the server — is exactly the bug that disabled this endpoint the first time:
a public prekey rotates with no private half anywhere (or with the bundle still holding the
previous one), and every grant addressed to the device becomes permanently unopenable, because §7
prefers the prekey once one is present. The server cannot verify the bundle actually opens or that
it contains the private half it claims to — the blob is opaque by design — but atomicity with the
public-key write is what it *can* guarantee, and it is what the fix turns on.

**Why rotation was disabled, for the historical record.** Grants were wrapped to
`signed_prekey_public ?? identity_public_key`, but the private half had nowhere to live: the
bundle was sealed under an Argon2id key derived from the password, and the password is not
retained after unlock, so re-sealing it to store a rotated private half would have meant
re-prompting on every rotation. This shipped once, was reverted, and the prekey columns were
cleared. The fix closing that gap is §2.2's `prekey_private`: generated at registration, alongside
the identity keypair, so it is already inside the bundle — and inside the in-memory KEK's reach —
by the time a rotation needs somewhere to put a new one.

### 2.2 Private key storage

The private halves are serialised as JSON, encrypted with AES-256-GCM under an Argon2id-derived
key, and stored server-side as an opaque blob:

```
KEK        = Argon2id(password, salt, m>=65536 KiB, t>=3, p=4, len=32)
plaintext  = {"signing_private": b64u, "identity_private": b64u, "prekey_private": b64u,
              "prev_prekey_private": b64u}
bundle     = AES-256-GCM(KEK, nonce, plaintext, aad=none)
```

`prekey_private` is the private half of the signed prekey (§2, §2.1.1). A client generates it at
registration, alongside `signing_private`/`identity_private`, so it is available immediately after
unlock with no extra password prompt — that immediacy is what makes rotation (§2.1.2) possible
without re-prompting for the password on every rotation.

`prekey_private` MAY be absent. A bundle sealed by a client that has not yet adopted this field —
every bundle sealed before rotation was re-enabled — has no such key, and the server has no way
to add it: the blob is opaque, so there is nothing to migrate server-side. A client MUST treat a
missing `prekey_private` as "this device has no usable prekey yet" and fall back to
`identity_private` for anything a peer wrapped to the identity key, exactly as it already does when
a peer's roster entry has no `signed_prekey_public` at all. The field starts appearing the moment
the bundle is next re-sealed for any reason — registration of a new device, prekey rotation, or a
change-password re-wrap — after which it is populated from then on.

`prev_prekey_private` MAY be absent, and normally is: it exists only during the one-rotation grace
window described in §2.1.2. It holds the private half of the signed prekey that rotation is about
to supersede, carried forward exactly once so a grant published against that outgoing prekey but
not yet ingested at rotation time can still be opened. On the *next* rotation after that, whatever
`prev_prekey_private` held is discarded outright — it is not accumulated into a history — and the
prekey generation being superseded by that second rotation takes its place. A client unwrapping a
grant MUST try, in order, the current `prekey_private`, then `prev_prekey_private` if present, then
`identity_private`, before reporting the grant unopenable.

`kdf_params` MUST accompany the blob: `{"kdf":"argon2id","m","t","p","salt","nonce"}`. The server
MUST reject `m < 19456` or `t < 2`.

> Because the wrapped bundle is stored on the server, a database disclosure yields an offline
> password-guessing target. The Argon2id parameters are therefore a security control, not hygiene.

### 2.3 Safety numbers

A safety number is a property of a *person*, but keys belong to devices, so each side's active
device signing keys are first collapsed into one 32-byte value:

```
material_X = SHA-512("NS-v1-fingerprint" || for each key in sorted(signing_pubs_X):
                                               u16be(len(key)) || key)[0:32]

digest = SHA-512("NS-v1-fingerprint" || sorted(material_A, material_B))
number = 12 groups of 5 digits, each = u32be(digest[4i:4i+4]) mod 100000
```

SHA-512, not SHA-256: 12 groups consume 48 bytes, and a 32-byte digest cannot fill them — the tail
groups would silently be zeros, displaying 60 digits while carrying 40 digits of entropy.

**Every active device contributes.** Deriving the number from a single arbitrarily chosen device
key made it depend on row ordering, and — worse — left it unchanged when a peer gained a device, so
a device the server planted did not show up as a key change.

Inputs are sorted at both levels so both peers compute the same value. Clients MUST display this
and MUST warn visibly when a peer's number changes. **This is the only defence against a malicious
server substituting a public key**, so the client MUST derive it itself, from key material whose
binding signatures it has verified (§5.0.2). A server-computed number is a convenience for
debugging only: a server asked to fingerprint a key it substituted will simply fingerprint the
original, and the client cannot tell.

## 3. Sender-key ratchet

Each sender owns one chain per (chat, epoch).

```
CK_0            = 32 random bytes
MK_i || N_i     = HKDF-SHA256(ikm=CK_i, salt="", info="NS-v1-msgkey", L=44)
                    MK_i = [0:32]   AES-256 key
                    N_i  = [32:44]  GCM nonce
CK_{i+1}        = HKDF-SHA256(ikm=CK_i, salt="", info="NS-v1-chain",  L=32)
```

Rules:

- A sender MUST discard `CK_i` immediately after deriving `MK_i`. This is what provides forward
  secrecy within an epoch.
- The nonce is **derived, not random**. Since `MK_i` is unique per index, `(key, nonce)` reuse is
  structurally impossible. Implementations MUST NOT substitute a random nonce.
- A receiver MAY retain keys for skipped indices to tolerate out-of-order delivery, bounded at
  **2000**; beyond that it MUST reject rather than derive unboundedly (denial-of-service vector).
- A receiver MUST NOT accept a chain index it has already consumed.
- Retained skipped keys SHOULD be expired; keeping them forever negates forward secrecy.
- A client that rebuilds receiver chains from the grant after a reload (section 3.1) re-derives, and
  so re-retains, keys for messages it has already read. See the trade-off stated there.

The chain is one-way, so handing a peer `CK_i` grants messages `i` onward and nothing earlier.

### 3.1 Retained skipped keys at rest (client-local)

Local storage format only. Nothing here crosses the wire, the server never sees it, and there is no
Python reference or interop vector. A client MAY mirror a receiver chain's retained skipped keys
(section 3) to durable storage so a late message still opens after a page reload. If it does:

```
wrap_key = HKDF-SHA256(ikm=KEK, salt="", info="NS-v1-skipped-key", L=32)
aad      = "NS-v1-skipped" || uuid(user) || uuid(chat) || u32be(epoch)
           || uuid(sender_key_id) || u32be(index)
record   = { iv: 12 random bytes, ct: AES-256-GCM(wrap_key, iv, MK_i || N_i, aad) }   (44-byte plaintext)
```

- `KEK` is the Argon2id-derived key that seals the private bundle (section 2.2). It is held in memory
  only, so entries cannot be opened without the password.
- The IV MUST be fresh random per write. The AAD binds user, chat, epoch, sender key and index: a
  record moved to another slot fails the tag check instead of yielding a wrong key.
- A record that fails to open (wrong KEK after a password change, tampering, relocation) MUST be
  discarded, never trusted. A record whose storage id disagrees with its own location MUST be
  discarded.
- An entry MUST be deleted when its key is consumed or evicted by the section 3 budget, SHOULD
  expire after 30 days, and total storage MUST be capped (client: 10,000 entries).
- Everything MUST be erased on lock, logout, password change, password reset and account deletion.
  If durable storage is unavailable the client falls back to memory only; opening a message never
  depends on it. A wipe that cannot be confirmed MUST be reported, not assumed.
- After a password change the KEK changes. Rows wrapped under the old one are erased at once and
  new rows use the new KEK.
- Storage ids (user, chat, epoch, sender key id, index) and the save time are not secret and are
  stored in the clear as lookup keys; only the message key and nonce are wrapped. The save time is
  not in the AAD, so someone with write access to storage can age or de-age a row. That only
  changes how long a row lives, never what it opens to.

**What this does and does not buy (read before relying on it).** This client does not persist the
chain position. After a reload the receiver chain restarts at the grant's start index, so that
already-read history can be opened again from the server's ciphertext. Walking forward from there
re-derives, and re-retains, the keys of messages the user has already read, up to the 2000-key
retention budget per chain. So the stored set is not "only what was skipped": it is up to the most
recent 2000 indices below the highest index seen, on every chain the user has opened. A row's save
time is set when it is (re)written, so a chain that is reopened keeps being refreshed.

The consequences, stated plainly:

- Forward secrecy for those messages is weakened on this device for as long as such rows exist.
  A row is bounded by the 30-day age limit from its last write, and the grant it is rebuilt from is
  itself pruned 30 days after its epoch closes (section 5.4). Together, a key can remain on disk for
  roughly 60 days after the epoch closed.
- The exposure requires **both** a copy of the browser profile (the IndexedDB rows) **and** the
  user's password (to derive the KEK). Device compromise alone yields only wrapped rows. A
  server-side attacker never sees them.
- It does not make consumption durable: a key consumed before a reload is re-derived after it, so a
  reload cannot be used to prove a message was not read.

The alternative, persisting only indices that were genuinely skipped relative to the previous
session's chain position, needs that position stored, and a position past a message makes that
message unreadable after a reload unless its plaintext is stored as well. That trades a bounded key
exposure for either lost history or stored plaintext, which is worse, so it is not done. An
implementation that cannot accept the trade-off SHOULD NOT persist skipped keys at all.

## 4. Message envelope

```
msg_aad = "NS-v1-msg"           (9)
       || chat_id               (16)
       || u32be(epoch)          (4)
       || sender_id             (16)
       || sender_key_id         (16)
       || u32be(chain_index)    (4)      = 65 bytes

ct  = AES-256-GCM(MK_i, N_i, plaintext, aad=msg_aad)
sig = Ed25519(chain_signing_private, msg_aad || SHA-256(ct))
```

```json
{ "v":1, "alg":"A256GCM-SK1", "epoch":5, "skid":"<uuid>",
  "idx":42, "n":"<b64u>", "ct":"<b64u>", "sig":"<b64u>" }
```

### 4.1 The AAD rule

**AAD MUST be reconstructed from trusted values, never read from the envelope.** `chat_id` comes
from the request path after the membership check; `sender_id` comes from the authenticated session.
Only `epoch`, `skid` and `idx` are client-supplied. If `chat_id` or `sender_id` were taken from the
envelope, a client could set them freely and the binding would prove nothing.

Each bound field blocks a specific attack:

| Field | Attack blocked |
|---|---|
| `chat_id` | copying a ciphertext into another chat the attacker belongs to |
| `epoch` | replaying a pre-removal message into the post-removal epoch |
| `sender_id` | the server relabelling the sender to misattribute a message |
| `skid` | confusion when one sender has two chains in an epoch (multi-device) |
| `idx` | reordering or index-shifting; also makes the derived nonce unique |

### 4.2 Verification order

A client MUST verify the signature **before** decrypting, and MUST NOT act on a message whose
sender it has not authenticated. The server SHOULD verify the signature on send (~50 µs) — it
cannot read the message but can prove the sender is who the envelope claims, which is the only
integrity check available to it.

### 4.3 Edits

An edit MUST be sealed under a **fresh chain index**. Re-encrypting under a consumed message key
repeats a `(key, nonce)` pair, which for AES-GCM leaks the XOR of both plaintexts and can expose the
authentication subkey. The server rejects `idx <= stored idx` with `CHAIN_INDEX_REUSED`.

The original ciphertext is destroyed, so there is no cryptographic edit history.

### 4.4 Content formats

`content_format` is **persisted**, not derived:

| Value | Meaning |
|---|---|
| `sender_keys_v1` | envelope present; current scheme |
| `legacy_rsa` | private chat under the superseded RSA scheme |
| `legacy_plaintext` | group/channel message from before encryption |

### 4.5 Attachment encryption

Attachments (photos, videos, gifs, voice notes) are encrypted entirely client-side, on top of the
mechanisms above rather than as a new one. For each attachment the client generates a random
32-byte AES-256-GCM key and a random 12-byte nonce, and uploads `nonce || ciphertext` as an opaque
blob through the existing `POST /files/upload` — the server stores and serves these bytes exactly
as it does any other attachment, with no awareness that they are encrypted.

The per-attachment key is not a new wire primitive: it travels to recipients inside the
`envelope`'s already-sealed, authenticated plaintext, alongside the message text, the same way the
message body itself does. This needs **no new domain separator** and **no change** to the
envelope, ratchet or grant mechanisms defined elsewhere in this document — an attachment key is
just more plaintext under the same seal.

Stickers are the one attachment kind exempt from this — they're public, unencrypted images served
from the sticker-packs bucket (see `_authorize_sticker_attachment` in `messages_service.py`), so
they carry no key and never appear in `attachmentKeys`.

Consequently there is no Python reference counterpart for this, unlike every other primitive in
this spec: the server never parses or touches this plaintext structure, so there is nothing on the
server side that needs to be kept byte-identical to the client, and nothing for `npm run interop`
to check here.

Only the `{url, key}` pair travels inside the sealed plaintext above; the rest of an attachment's
metadata (`name`, `size`, `content_type`, `kind`, `duration_ms`, `width`, `height`, `waveform`) is
carried on the message document itself and is therefore server-asserted, not authenticated by the
envelope. A malicious server could in principle relabel a displayed name, size or kind without the
client detecting it — but it cannot swap the actual ciphertext content undetected, since GCM fails
closed on any key/ciphertext mismatch. This is a metadata-display-trust caveat, not a gap in
content confidentiality or integrity.

Editing a message's attachment list and the envelope's `attachmentKeys` are two separate pieces of
state that must be updated **together**, in the same edit. The Mongo-stored attachment metadata
(`url`, `name`, `kind`, ...) is one thing; the per-attachment decryption key carried inside the
sealed envelope's authenticated plaintext is another, and nothing on the server links the two or
checks they stay consistent — it cannot, since it never sees the plaintext. A client that adds an
attachment to `PUT /messages/{id}` without also re-sealing an envelope whose plaintext carries a
matching key for it leaves the recipient with an attachment listed but no way to decrypt it: the
key never reaches the wire except inside that authenticated plaintext, so there is nowhere else for
it to come from. `MessageService.editText` maintains this by construction: it builds the fresh
plaintext's `attachmentKeys` from the same attachment list it sends to `PUT /messages/{id}` in the
same call, and refuses to proceed if any kept attachment is missing its decryption key, rather than
silently persisting an unreadable attachment. This check correctly exempts sticker-kind attachments
— they never carried a key to begin with, so requiring one would make editing any message that
happens to carry a sticker impossible, including a pure text-only edit.

### 4.6 Poll control messages

A poll is an ordinary sealed message whose plaintext payload describes it. A vote or a close marker is
a *control message*: an ordinary sealed message (same envelope, AAD, signature, epoch enforcement,
`client_message_id` idempotency and rate limit) that additionally carries two fields outside the
envelope:

| Field             | Type            | Rule                                                              |
|-------------------|-----------------|-------------------------------------------------------------------|
| `is_control`      | bool, default 0 | `true` marks a vote or close message.                             |
| `poll_message_id` | 24-hex ObjectId | Required iff `is_control`; forbidden otherwise. Names the poll.   |

The server checks that the poll exists in the **same chat**, is not itself a control message, and that
the chat is a `sender_keys_v1` private or group chat (never a channel or a legacy chat). A control
message carries no reply, forward or attachments and cannot be edited, reacted to or pinned. Edits never
change either field. It is not counted as unread, never becomes a chat's `last_message`, does not
reorder the chat list and is absent from `GET /chats/{id}/messages`. It is served by
`GET /messages/{chat_id}/polls/{poll_message_id}/votes?limit=&before=` (newest first, default 100,
max 200, same history floor as normal history), and is published as a normal `new_message` event.
Deleting the poll deletes its control messages; users cannot delete a control message themselves (`409 CONTROL_MESSAGE_NOT_ALLOWED`): a voter retracts by voting again, and a close marker cannot be removed to reopen a poll.

Limits, enforced before anything is stored: the envelope `ct` of a control message may not exceed 4096 characters (`422 CONTROL_MESSAGE_TOO_LARGE`), and one sender may hold at most 50 control messages per poll (`409 CONTROL_MESSAGE_LIMIT`; the count is not atomic, so a concurrent burst can overshoot slightly). `CONTROL_MESSAGE_NOT_ALLOWED` is `422` when the chat or shape can never carry a control message (channel, legacy chat) and `409` when an operation is attempted on an existing one (react, pin, delete). `GET .../votes` is rate limited per user.

The server cannot tell that a message *is* a poll: a poll is an ordinary message, so editing it with `PUT` works and keeps `is_control` false.

**Ordering is not a chronology.** Pagination and "newest first" follow the ObjectId. Across several API workers an ObjectId is only reliably ordered at second granularity, so two votes sent within the same second may be listed out of true order. Clients order votes by ObjectId, as they do all messages; it is a total order for everyone, not a proof of which was sent first.

**Metadata leak.** The fields are unencrypted by necessity. The server learns that a message is a vote
or a close marker, which poll it belongs to, who sent it and when. It never learns the question, the
options or the chosen answer: those live only in the sealed payload. Anonymity of votes is a
client-side presentation choice only; every control message is signed by its sender's chain key.

### 4.7 Typed plaintext payloads (polls, votes, locations)

The plaintext half of the poll control messages of §4.6. Like attachment keys (§4.5), these live **inside** the sealed plaintext: no change to the envelope,
ratchet, AAD or grants, nothing for `npm run interop` to check, and the server never parses them.

A plain text message keeps the original shape, `{"text": ..., "attachmentKeys": [...]}`. A typed
payload adds `v` (currently `1`) and `type`, one body object named after the type, and a `text`
fallback (and an empty `attachmentKeys`) so an older client shows a readable line instead of JSON:

| `type` | Body | Limits |
|---|---|---|
| `poll` | `poll: {question, options[], multiple, anonymous, closes_at?}` | question 1-300 chars; 2-10 options of 1-100 chars; `multiple`/`anonymous` booleans; `closes_at` ISO-8601 or null |
| `poll_vote` | `poll_vote: {poll_id, options[]}` | `poll_id` 24-hex ObjectId of the poll message; 1-10 distinct integer indices in 0-9 (exactly one unless the poll is `multiple`) |
| `poll_close` | `poll_close: {poll_id}` | as above |
| `location` | `location: {lat, lon, accuracy?, label?}` | finite numbers rounded to 6 decimals (about 0.1 m), lat in [-90, 90], lon in [-180, 180]; accuracy >= 0; label clamped to 100 chars |

**Control messages.** `poll_vote` and `poll_close` are sent with the server-visible `is_control: true`
and `poll_message_id` (the poll they refer to). The server uses these only to keep them out of
history, unread counts and previews, and to list them per poll; it cannot read them. Everything
else is the client's job, and a vote counts only if all of these hold:

- it decrypted and its signature verified (an unreadable or unverified control message is ignored);
- `poll_message_id` and the sealed `poll_id` both equal the poll being tallied. The first is
  unauthenticated metadata, the second is signed; requiring both stops a vote being replayed into
  another poll by whoever controls either field;
- its id is greater than the poll's (ObjectIds are chronological), and the sender is a current member;
- for a single-choice poll it names exactly one option; an invalid vote is skipped and never erases
  an earlier valid one.

Per voter the latest valid vote by message id replaces earlier ones. Only the poll's author can
close: the earliest valid `poll_close` from the author wins, and votes after it (or created after
`closes_at`) are ignored. If the poll message is deleted its votes are ignored.

**Edit and delete.** The server lets a poll's author re-seal the poll message (`PUT`), which can
change the question or options under existing votes; the UI never offers it. A client that finds the
poll message edited counts only votes created at or after `edited_at` and says so on the card. Deleting
the poll deletes its control messages; deleting an individual vote or close is refused by the server
(`409 CONTROL_MESSAGE_NOT_ALLOWED`). Votes are capped server-side per (poll, sender), so changing one's
mind has a limit, and a control message's ciphertext is capped (4 KB).

**What a tally is worth.** It is computed by each client from the list of control messages the server
returns, in the order of the server's ObjectIds. Each message is authenticated (signed by its sender's
chain, whose owner is bound at distribution ingest), so the server cannot forge a vote or change who
cast it. It *can* omit votes, delay them, or order them: dropping a voter's newest vote makes an
older one stand, and dropping a close lets a poll appear open. A malicious server can therefore bias a
result, and different members can in principle be shown different results. Clients show a warning when
the list is truncated or votes could not be read, but cannot detect omission. A member who leaves or is
removed stops counting: their votes disappear from the tally once they are not in the roster.

**Receive-side strictness.** The same validators run on send and on receipt. A payload whose `type`
is unknown, whose `v` is newer than understood, whose body is malformed, oversized or contains
`NaN`/out-of-range numbers, or which is misplaced (a vote that is not a control message, or a
control message that is not a vote or close) is shown as an *unsupported message*, never as text and
never counted. Optional labels are clamped rather than rejected.

**Anonymous polls are anonymous in the interface only.** The server sees who sent every vote (it is
a message from a known account to a known poll), every message is signed with the sender's chain key
so a vote is cryptographically attributable to its sender, and any member's client can decrypt it.
`anonymous: true` makes an honest client omit voter identities from the tally and the export; the
server knows who voted, and other members' browsers can read it too. The interface merely hides it.
The UI says exactly this next to the "Anonymous" label. Real anonymity would need blind signatures
or ring signatures over a channel unlinked from the sender, which this protocol does not have.

## 5. Key epochs and grants

An epoch is `(chat_id, epoch, member_set_hash, reason)` and carries **no key material**. The server
therefore allocates epochs unilaterally; there is no nominated rotator and no state in which the
group cannot send.

Key material is supplied lazily and independently by each **sender**, on first send into the epoch.
A member who never sends never publishes a chain and never pays the wrapping cost. Two senders
publishing into the same epoch is normal and correct — the chains are independent.

A sender MUST publish grants covering **exactly** the epoch's member device set. A partial upload
is rejected: it is either a client bug or an attempt to silently exclude a member.

```
record          = device_id || ":" || identity_public_key || ":" || signing_public_key
                            || ":" || signed_prekey_public      (empty string where absent)
member_set_hash = SHA-256("NS-v1-memberset-v2" || "|".join(sorted(records)))
```

Every field is unpadded base64url or a hyphenated uuid, and neither `:` nor `|` occurs in either
alphabet — so no field value can forge a record boundary and no two distinct rosters collide.

**The hash commits to the key material, not only to the device ids.** Hashing ids alone (the `v1`
form, `"NS-v1-memberset"`) left the whole check defeatable without touching the device set: a
server could return the same devices with one member's `identity_public_key` replaced by a key it
held, or inject a `signed_prekey_public` of its own — which §5.1 *prefers* as the ECDH recipient —
and the hash was unchanged. Every sender then wrapped the chain key for the server.

### 5.0 Distribution signature

A chain's per-chain signing key MUST be vouched for by the sender's long-term identity key:

```
payload   = "NS-v1-skdm" || chat_id(16) || u32be(epoch) || sender_key_id(16)
                         || chain_signing_public(32) || u32be(chain_start_index)
signature = Ed25519(identity_signing_private, payload)
```

The server verifies this on publish, so it cannot store a distribution the claimed sender never
made. Binding chat and epoch stops a valid distribution being relocated.

### 5.0.1 Group size

Grants cost `S x (N-1)` per epoch, where `S` is the number of members who actually send. This is
enforced, not merely documented: encrypted chats are capped at **256 members**. Signal caps groups
at 1000 and WhatsApp at 1024; those limits exist for the same reason.

### 5.0.2 Roster verification (client-enforced)

Before wrapping keys for an epoch, a client **MUST** do both of the following and refuse to proceed
on any failure. Neither alone is sufficient.

**1. Verify every roster entry's binding signature.** Each entry carries `identity_key_signature`
over §2's binding, and `signed_prekey_signature` over §2.1.1's where a prekey is present. A prekey
without a valid signature MUST be rejected outright, not silently ignored in favour of the identity
key — ignoring it hides the fact that a key was injected.

This is the root of trust, because the signing key is what a peer pins out of band as a safety
number (§8). To substitute a key a server would have to substitute the signing key too, which
changes the safety number and becomes visible to anyone who has verified their peer.

**2. Recompute `member_set_hash` from the roster** and compare it against the epoch's commitment.
This catches a roster that disagrees with the set the server committed to when the epoch opened.

The commitment MUST be the value stored on the epoch row when it was allocated. A server that
recomputes it from the roster it is currently returning makes the comparison tautological — the
client hashes the same list the server just hashed, so it matches for any list at all, ghost devices
included. `GET /crypto/chats/{id}/roster` returns the stored value for exactly this reason.

The backend **cannot** enforce either check; both live entirely in the client. The server writes the
commitment as well as the roster, so on its own the hash only proves internal consistency — check 1
is what makes check 2 mean anything.

### 5.1 Grant wrapping

```
E_priv, E_pub = X25519 keygen (fresh per grant)
R_pub         = recipient signed_prekey if present else identity key
ss            = X25519(E_priv, R_pub)

grant_aad = "NS-v1-grant" || chat_id(16) || u32be(epoch) || sender_key_id(16)
                          || sender_device_id(16) || recipient_device_id(16) || E_pub(32)

wk || wn  = HKDF-SHA256(ikm=ss, salt=SHA-256(chat_id || u32be(epoch)), info=grant_aad, L=44)
wrapped   = wn || AES-256-GCM(wk, wn, CK_start(32) || u32be(start_index), aad=grant_aad)
```

Binding `E_pub` into both the AAD and the HKDF info blocks reuse of a captured ephemeral.

### 5.2 Rotation triggers

| Event | Rotate? |
|---|---|
| Member removed / left | **Yes, mandatory** — the only thing that stops future reads |
| Member added, history `JOINED` | Yes |
| Member added, history `SHARED` | No — existing members backfill grants |
| Device revoked | Yes |
| Periodic | Yes |
| **Role changed** | **No** — roles are authorization, not a confidentiality boundary |

A removed member retains everything they already held. This is unavoidable and MUST be stated in
the UI rather than implied otherwise.

Rotation is atomic with the membership change that triggered it. A removal that committed without
its rotation would leave the departed member able to read anything sent in the interim.

### 5.3 Send-path enforcement

The server rejects a message that is not keyed to the live epoch:

| Condition | Error |
|---|---|
| Chat is encrypted, plaintext supplied | `400 ENVELOPE_REQUIRED` |
| `envelope.epoch != current_epoch` | `409 EPOCH_STALE` |
| No distribution for `(epoch, skid)` | `409 SENDER_KEY_MISSING` |
| Distribution belongs to another member | `403 SENDER_KEY_NOT_YOURS` |
| Signature fails against the published chain key | `400 INVALID_MESSAGE_SIGNATURE` |

Epoch equality is **strict**, with no grace window — a window is exactly the gap that lets a
message composed before a removal land after it.

### 5.4 Scheduled maintenance

Periodic rotation runs daily and re-keys any chat past its rotation interval, **skipping chats with
no traffic in the current epoch**: rotating a dormant conversation only creates epochs nobody will
publish keys for.

Grant pruning drops grants for epochs closed longer than 30 days once every recipient has fetched
them. Distributions are never pruned — they hold the signing keys needed to verify historical
message signatures.

## 6. Channels — signed, not encrypted

Channels are deliberately **outside** the end-to-end trust boundary. This is a reasoned scoping
decision, and the reasoning belongs in the write-up rather than being hidden:

1. **Confidentiality is unachievable for open broadcast.** A channel anyone may subscribe to hands
   its content to any adversary who subscribes. Encryption does not change that.
2. **Sender keys do not survive the scale.** Grants cost O(N) per rotation, wrapped on a single
   client, and every unsubscribe forces a rotation. At a few thousand subscribers with normal churn
   a client cannot finish wrapping before the next epoch opens — the system thrashes and never
   converges. The crossover is roughly N ≈ 500–1000, which is why Signal caps groups at 1000 and
   WhatsApp at 1024.
3. **Deployed messengers agree.** Telegram channels and WhatsApp Channels are both server-readable.

**Integrity is not meaningless, and is preserved.** Every post is signed:

```
payload = "NS-v1-post" || chat_id(16) || sender_id(16) || post_id(16) || SHA-256(content)
sig     = Ed25519(identity_signing_private, payload)
```

`chat_id` and `sender_id` stop a post being relocated or reattributed; `post_id` makes each
signature unique so a captured `(content, signature)` pair cannot be replayed as a second post;
the content hash makes it tamper-evident.

Cost is O(1) per post regardless of subscriber count, with no key distribution whatsoever.

Posting is restricted to OWNER and ADMIN. The server verifies the signature on publish, so a stored
post is always one its claimed author actually signed. `POST /crypto/chats/{id}/enable` refuses
channels outright rather than silently applying a scheme that cannot scale.

> The distinction worth stating plainly: **for public broadcast, confidentiality is meaningless but
> authenticity is valuable.** Securing what can actually be secured is a stronger position than
> claiming end-to-end encryption everywhere.

## 7. What this does not protect

State plainly; do not overclaim.

- **Metadata.** The server sees the social graph, group membership, timing, message sizes, presence,
  typing indicators, read receipts and the reply graph. For many realistic adversaries this is more
  valuable than the content.
- **Malicious participants.** E2E provides no protection against someone in the chat. They can read,
  screenshot and exfiltrate everything they have keys for.
- **Compromised devices.** Full exposure of everything that device holds.
- **Self-destructing messages.** A UX affordance, not a security guarantee.
- **Forward secrecy across epochs only.** Within an epoch the ratchet protects earlier messages, but
  post-compromise security requires rotation; this is not MLS or a full double ratchet.
- **Web delivery.** The server ships the JavaScript that performs the encryption, so it could ship
  backdoored code. Mitigations: Subresource Integrity, reproducible builds, or a signed native
  client. E2E in a browser has a weaker trust model than E2E in a signed native app.
