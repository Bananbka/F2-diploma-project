# План: персональна черга подій та стійкість клієнта

Останній пакет змін поточної серії. Одна гілка, один Pull Request. Охоплює TB-17…20
(мінімальна версія персональної черги подій на Redis Streams) і TB-30…32 (стійкість клієнта
під час розподілу ключів).

## 1. Персональна черга подій (TB-17…20)

Рішення власника: мінімальна версія, без consumer group на кожне з'єднання і без XACK.

- **TB-18.** Розсилання виноситься з модуля маршрутизатора в порт `EventPublisher` та
  реалізацію `RedisEventPublisher`. Сервіси залежать лише від порту.
- **TB-19.** Усі події одного відправлення йдуть одним `pipeline()` Redis замість N
  послідовних операцій.
- **TB-17.** Кожна подія для користувача записується в потік `stream:user:{id}`
  (`XADD ... MAXLEN ~ N`, TTL потоку 30 днів) і, як і раніше, публікується в канал
  `user:{id}` для живої доставки. Подія несе поле `stream_id`.
- **Курсор.** Клієнт запам'ятовує останній `stream_id`. Під час перепідключення він передає
  його (`/ws?cursor=<id>`); сервер до переходу в живий режим відтворює події після курсора
  (`XRANGE`). Якщо курсор старший за межу потоку або його не існує, сервер надсилає подію
  `resync_required`, і клієнт перезавантажує стан через HTTP, як раніше. Без курсора
  поведінка не змінюється.
- **Дедуплікація** лишається на клієнті за ідентифікатором повідомлення; повторна доставка
  безпечна.
- **TB-20.** Збій розсилання після збереження повідомлення журналюється і не змінює
  відповідь: вона лишається 201, бо 5xx призвів би до дубліката. Додається тест.
- **Не входить:** consumer group на з'єднання, XACK, окремі гарантії порядку на сервері.
  Формулювання «гарантія доставки» у документації лишається поміркованим: потік дає
  відновлення пропущених подій у межах TTL, а не підтверджену доставку.

- **Окремий Redis для подій (відхилення від backlog).** Усі події (потоки, pub/sub, маркери
  прогалин, replay) живуть в окремому сервісі `redis-events` (`EVENTS_REDIS_URL`,
  `EVENTS_REDIS_PASSWORD`), а не в основному `redis`. Вимоги протилежні: основний Redis тримає
  список відкликаних токенів, `force_logout`, OTP, rate limits, присутність і брокер Celery, тому
  він `noeviction` і зберігається на диск; `redis-events` має `--maxmemory 256mb
  --maxmemory-policy allkeys-lru --save "" --appendonly no`, не публікується на хост і
  вимагає пароль. У backlog TTL потоку 30 днів, реалізація використовує
  `EVENT_STREAM_TTL_SECONDS` = 7 днів, `EVENT_STREAM_MAXLEN` = 200 і ліміт запису 32 КБ
  (`EVENT_STREAM_MAX_ENTRY_BYTES`). Подія понад ліміт або така, яку Redis відхилив, не
  зберігається: вона публікується наживо, а для користувача ставиться маркер `stream-gap:{id}`.
  Підключення з курсором не новішим за маркер отримує `resync_required` з причиною
  `stream_gap`; тож надвелика подія свідомо призводить до перезавантаження через HTTP.
- **Витіснення та перезапуск.** Дані подій лише в пам'яті: без RDB/AOF. Під тиском пам'яті
  Redis витісняє цілі потоки, після перезапуску порожньо. В обох випадках клієнт із курсором
  отримує `resync_required` (`stream_missing` або `cursor_too_old`) і перезавантажує стан;
  це перевіряє тест. Залишковий випадок: якщо витіснено лише сам маркер прогалини, а потік
  лишився, прогалина непомітна; ймовірність мала, бо маркер оновлюється разом із потоком.
- **Часткова відмова розсилання.** Розсилання для кількох отримувачів виконується пакетами по
  500 без загальної транзакції: якщо збій станеться посередині, частина отримувачів уже отримала
  подію, решта ні, і про це немає окремого сигналу (збій лише журналюється; такі отримувачі
  наздоганяють HTTP-перезавантаженням). Видалення повідомлення не виконує `XDEL` для копій, що вже
  стоять у потоках, вони зникають за TTL/витісненням/перезапуском (не довше 7 днів).

## 2. Стійкість клієнта (TB-30…32)

- **TB-30.** Публікація ключа відправника: не більше 3 спроб із затримкою `2^n × 250 мс` для
  мережевих помилок, 5xx, `EPOCH_CLOSED` і `GRANT_SET_MISMATCH`. Невдала перевірка складу
  (`MEMBER_SET_MISMATCH`, `ROSTER_VERIFICATION_FAILED`) не повторюється, надсилання
  блокується. Помилки клієнта типізуються за назвами з алгоритму 2.6.4.3.
- **TB-31.** `EPOCH_STALE`: один повтор із тим самим `client_message_id` для
  `details.current_epoch`; після другої відмови стан «не надіслано» з кнопкою «Повторити».
  Спершу звіряється наявна поведінка, зайвого не переписується.
- **TB-32.** `ReceiverChain.skipped` зберігається в IndexedDB під ключем, обгорнутим KEK,
  щоб пізні повідомлення відкривалися після перезавантаження сторінки. Зміна торкається
  криптографічного шару: потрібні `npm run interop`, огляд безпеки й опис у
  `docs/crypto-spec-v1.md`, якщо змінюється формат зберігання.
