# План: безпекове загартування та ідемпотентне надсилання

Документ фіксує, які пункти з беклогу доведення застосунку до специфікації (TB-01…TB-47) було
відібрано до реалізації, які відкладено і чому. Усе відібране виконується однією гілкою та
одним Pull Request.

Стан пунктів звірено з кодом гілки `main` 24.10.2026.

## 1. Критерій відбору

Береться те, що:

- закриває реальну вразливість або невідповідність коду контракту;
- підсилює головну тему роботи (месенджер з наскрізним шифруванням);
- реалізується малою зміною з перевірюваним результатом.

Не береться операційна обв'язка, яку не можна перевірити без реального сервера, та
косметичні зміни, що ламають клієнта без користі для захисту.

## 2. Що реалізується

### 2.1. Безпека (AppSec)

| Пункт | Зміна | Прийняття |
|---|---|---|
| TB-01 | У Redis зберігається `HMAC-SHA256(SECRET_KEY, otp)`; порівняння через `hmac.compare_digest`. TTL 900 с і ліміт 5 спроб не змінюються | У Redis немає 6-значних кодів; наявні тести OTP проходять |
| TB-02 | Ключ denylist: `blacklist:{sha256(token)}`. Перевірка читає обидва формати, поки не спливе TTL refresh-токена | У Redis немає JWT у відкритому вигляді; тести виходу та `force_logout` проходять |
| TB-03 | Перевірка `Origin` до `accept()` у WebSocket за списком `ALLOWED_WS_ORIGINS`; відмова з кодом 1008 | Чужий Origin отримує відмову, дозволений встановлює з'єднання |
| TB-04 | Прапорець `EXPOSE_API_DOCS` (за замовчуванням `false`) керує `docs_url`, `redoc_url`, `openapi_url` | У конфігурації без прапорця `/docs` і `/openapi.json` повертають 404 |
| TB-05 | `ConfigDict(extra="forbid")` для всіх request-моделей, що змінюють стан | Запит із зайвим полем (`role`, `is_verified`) отримує 422; Pytest і Karma зелені |
| TB-06 | `max_length=10` для `attachments` у моделях створення та редагування повідомлення | 11 вкладень дають 422 |
| TB-12 | Заголовок `Retry-After` у відповіді 429 застосунку; JSON-тіло 429 і `Retry-After` на шлюзі. Виправлено також мертвий регулярний location для жорсткого ліміту облікових маршрутів (його перекривав `^~ /api/`) | Відповідь 429 має JSON-тіло `ErrorResponse` і заголовок |
| TB-29 | Задача `send_email`: `autoretry_for=(SMTPException, OSError)`, `max_retries=3`, `retry_backoff=True` | Тест перевіряє повтор після збою SMTP |

### 2.2. Контракт API та ідемпотентність

| Пункт | Зміна | Прийняття |
|---|---|---|
| TB-13 | Поле `client_message_id` (UUID) у запиті та документі; частковий унікальний індекс `ux_chat_sender_client_msg`; повтор повертає наявний документ з кодом 200 і повторно розсилає подію (клієнти дедуплікують за id), щоб збій між записом і розсилкою не губив доставку. Повтор того самого ключа з іншими reply, вкладеннями чи форматом дає 409 `IDEMPOTENCY_KEY_REUSED`; шифротекст у відбиток не входить, бо ручний повтор перешифровує повідомлення. Клієнт генерує UUIDv4 до шифрування й зберігає його під час повторів, зокрема після `EPOCH_STALE` | Два однакові запити дають один документ; друга відповідь має той самий `_id` |
| TB-10 | `POST /messages` без кінцевої скісної риски; старий шлях лишається прихованим із схеми | `POST /api/messages` повертає відповідь без переадресації 307 |
| TB-11 | Код 201 для `POST /messages` (новий документ) та `POST .../sender-keys`; клієнт приймає 200 і 201 | Новий ресурс дає 201, повтор дає 200 |
| TB-14 | `edited_at` записується під час редагування й віддається у `MessageResponse` | Тест редагування перевіряє поле |

## 6. Обмеження

- Коміти без співавторів та підписів Claude; файли `CLAUDE.md` і `.claude/` не комітяться.
- Після будь-якої зміни криптографічного шару виконується `npm run interop`.
- Інтеграційні тести виконуються з увімкненим rate limiting.
- Додані налаштування (`ALLOWED_WS_ORIGINS`, `EXPOSE_API_DOCS`) мають потрапити в `Settings` та
  `src/api/.env`; невідомі змінні там ігноруються мовчки.
